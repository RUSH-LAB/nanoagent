# RUSH Lab cloud on AWS

RUSH Lab cloud runs members' plugins on a server, so a member needs nothing but a browser. This
page is the operator's runbook: what it is, how it is secured, what it costs, and how to deploy,
check, roll back and run it. The code is in `src/server/cloud-runs.js` and `src/server/runner.js`;
the deployment is in `infra/aws/` and `scripts/aws/`.

## What members see

A site offers RUSH Lab cloud when Mochi starts with `CLOUD_RUNS=on`. Each member then chooses
where their plugins run:

- **RUSH Lab cloud.** Nothing to install, on any computer. Their plugin runs, installs and plugin
  pages are on the runner. Runs use the lab's OpenRouter key and count against the workspace's AI
  budget: $1 a day and $10 a month per workspace, $0.50 a day per member, unless an administrator
  changes them. NanoAgent caps each run at $0.10.
- **Their computer.** RUSH Lab, the desktop app, runs them with their own key, as before.

A member who has not chosen runs on their computer. While that computer is not connected, the
arrival screen offers RUSH Lab cloud first, in one click; Settings → Connection switches either
way. Nothing switches for them: a member on their computer is refused while it is not connected,
and a member in the cloud is never sent to their computer. Chat and inline completion stay on the
member's computer; RUSH Lab cloud runs plugins only.

A site that stops offering RUSH Lab cloud (`CLOUD_RUNS` unset) runs every member's plugins on
their computer again. Each member's choice is kept, and applies again once the site offers it.

## How it fits together

```text
browser ──HTTPS──► web VM: Caddy ──► Mochi (helpinghands/Dockerfile) ──► Neon PostgreSQL
                                        │  NanoAgent /v1, bearer token, inside the VPC
                                        ▼
                   runner VM: NanoAgent (nanoagent/Dockerfile), sandbox=bwrap ──► OpenRouter
                                        │  each plugin in its own bubblewrap sandbox
                                        ▼
                              egress proxy ──► only the hosts that plugin declares, over HTTPS
```

- **Web VM** (t4g.small): Caddy terminates TLS with a Let's Encrypt certificate for the domain
  and passes server-sent events and WebSockets through. Mochi is the unchanged production image.
- **Runner VM** (t4g.medium): the unchanged NanoAgent image, started by `infra/aws/runner/run.sh`
  with Railway's configuration plus `sandbox=bwrap`, `include_reasoning=true` and run folders on
  its data volume. It also packs marketplace plugins, as Railway's NanoAgent does.
- **The rest:** Neon PostgreSQL (unchanged), ECR for the images, SSM Parameter Store for the
  settings, CloudWatch Logs, and Session Manager instead of SSH.

## Security

Anyone can publish a plugin, so the runner treats every plugin as hostile. In layers:

1. **NanoAgent's sandbox.** Each plugin process runs under bubblewrap with an empty environment,
   its own folder read-only, only its run's folder writable, no network, and an egress proxy that
   reaches only the hosts it declares, over HTTPS, at public addresses. That refuses the instance
   metadata address and the VPC. NanoAgent proves the sandbox confines before it serves anything,
   and refuses to start where it does not.
2. **The container.** `infra/aws/runner/run.sh` documents each flag:
   - uid 10001, no capability, no new privileges;
   - a read-only root;
   - memory, CPU and process limits, which NanoAgent does not set itself;
   - Docker's default seccomp profile plus one rule for the five calls bubblewrap needs
     (`infra/aws/runner/seccomp.json`, generated by `scripts/aws/seccomp.mjs`);
   - `/proc` unmasked for bubblewrap's own;
   - a `bwrap` of its own ahead of the image's (`infra/aws/runner/bwrap`). A plugin can make no
     user namespace of its own, so it never has the kernel's namespace and netfilter calls that
     the seccomp rule lets bubblewrap make. And a plugin's processes are the first the kernel
     stops when the container runs out of memory, so a plugin never takes NanoAgent down with it.

   `npm run cloud:verify` shows NanoAgent refusing to start without the seccomp rule. A probe
   plugin there finds every one of these held. Without the `bwrap`, it can make a user namespace,
   and its processes filling the memory stop NanoAgent instead.
3. **The VM.** The runner VM is separate from the website. It holds only the NanoAgent token and
   the lab's OpenRouter key: no database URL, no sign-in secret. Its security group lets only the
   website reach NanoAgent's port, and lets the VM out only on 443. IMDSv2 is required with one
   hop, so containers cannot reach the VM's credentials. Its role can read only its own and the
   shared parameters, pull its own image and write its own log. Session Manager's managed policy
   would let it read every parameter in the account, so the role denies the rest explicitly.

What remains:

- A kernel exploit that escapes bubblewrap and the container lands on the runner VM, with that
  token, that key and that role. The next step is a microVM per run
  (`nanoagent/docs/plans/plugin-sandbox.md`, option 2).
- Members share the runner's limits. A plugin can hold the container's process limit or its
  memory for as long as its run lasts, at most NanoAgent's 180 s, and other members' plugins
  cannot start meanwhile. NanoAgent keeps serving, and the plugin's processes end with its run.
  A run that started a tool is charged, at $0.10 when NanoAgent did not price it, so a member's
  budget bounds how often they can do this.
- `CLOUD_RUNS` must never be set on a deployment whose NanoAgent runs plugins unconfined, such as
  Railway's (`sandbox: none`). Only the AWS rollout sets it, and only beside this runner.

## Cost

Estimated in us-east-1 at on-demand rates. These come from third-party price trackers dated 2026;
confirm them in the AWS Pricing Calculator.

| Item | Per month |
|---|---|
| Web VM, t4g.small | $12.30 |
| Runner VM, t4g.medium | $24.50 |
| Disks, 20 + 40 GB gp3 | $4.80 |
| Two public IPv4 addresses | $7.30 |
| ECR, CloudWatch Logs, two alarms | about $2 |
| **Total** | **about $51** |

Neon is unchanged. OpenRouter is bounded by the AI budgets above and by the runner key's own
limit. A one-year Compute Savings Plan takes about 28% off the VMs.

## Before the first deploy

1. **AWS.** An account, and AWS CLI credentials that may deploy CloudFormation stacks with EC2,
   IAM roles, ECR, SSM and CloudWatch Logs. Docker with buildx on the machine that deploys.
2. **A domain.** Choose it, and set `domain` in `infra/aws/deploy.yaml`. After the first deploy,
   point its A record at the stack's `WebAddress`. Use DNS only, not a proxy.
3. **A GitHub OAuth App** for the domain, with callback `https://<domain>/api/auth/callback/github`.
4. **A database.** A Neon branch or project for this site, with the schema owner's direct URL
   and a pooled URL for the runtime role `mochi_runtime` with a password of its own. The first
   start creates that role (`scripts/db/bootstrap-runtime-role.mjs`).
5. **An OpenRouter key for the runner**, with a spend limit.
6. **The settings**, as SecureStrings under `/rush-lab/<stack>/`. The stack writes
   `web/NANOAGENT_URL` itself:

   ```bash
   stack=rush-lab-cloud   # infra/aws/deploy.yaml's stack
   put() { aws ssm put-parameter --type SecureString --overwrite --name "/rush-lab/$stack/$1" --value "$2" >/dev/null; }
   put shared/NANOAGENT_API_TOKEN "$(openssl rand -hex 32)"
   put runner/OPENROUTER_API_KEY "sk-or-..."
   put web/BETTER_AUTH_SECRET "$(openssl rand -hex 32)"
   put web/DATABASE_MIGRATION_URL "postgresql://neondb_owner:...@...neon.tech/neondb?sslmode=require"
   put web/DATABASE_URL "postgresql://mochi_runtime:...@...-pooler...neon.tech/neondb?sslmode=require"
   put web/GITHUB_CLIENT_ID "..."
   put web/GITHUB_CLIENT_SECRET "..."
   put web/ROOT_GITHUB_LOGIN "..."
   put web/OPENROUTER_MANAGEMENT_KEY "..."
   put web/RESEND_API_KEY "..."
   put web/MAIL_FROM "RUSH Lab <noreply@...>"
   ```

   `OPENROUTER_MANAGEMENT_KEY` gives members' computers their keys, as on Railway. Mochi refuses to
   start without it. `MAIL_WEBHOOK_URL` can replace the two Resend settings.

## Deploy

Deploy from a clean checkout whose commit is on `origin/<branch>`, `production` by default:

```bash
npm run aws:deploy -- --dry-run   # prints every command; runs nothing on AWS or Docker
npm run aws:deploy
```

`scripts/aws/deploy.mjs` runs these steps in order and stops at the first that fails:

1. Checks the commit.
2. Checks every setting is set.
3. Deploys `infra/aws/stack.yaml`. A new stack's VMs get the latest Amazon Linux 2023, and keep
   it: a new image replaces both VMs, so a deploy changes it only when `deploy.yaml` names one
   (`image_id`).
4. Builds both images for arm64 and pushes them, tagged with the commit. An image already pushed
   is deployed as it is, as tags in the stack's repositories never change.
5. Rolls out the runner, then the website, through SSM Run Command. Each VM waits for its first
   boot to finish, checks out the commit and runs its `infra/aws/rollout.sh`. The runner's also
   starts the sweep of its run folders (`infra/aws/runner/sweep.sh`).
6. Waits for `https://<domain>/api/health`.

A rollout replaces the containers, so in-flight runs end. A cloud run's session says so as soon as
its member opens it, and takes a new message.

## Check it

- `https://<domain>/api/health` answers, and Mochi's startup log says
  `RUSH Lab cloud: offered (CLOUD_RUNS=on)`.
- Sign in, choose RUSH Lab cloud, install a plugin from the marketplace, and run it. The result
  card shows its verifier's verdict.
- Logs are in CloudWatch, in `/rush-lab/<stack>/web` and `/rush-lab/<stack>/runner`.
- `npm run cloud:verify` runs the runner check against the same commit, on any machine with Docker.

## Roll back

Check out an earlier commit on the branch and deploy it. Images are kept by commit, and the
rollout pulls the one it is given. As on Railway, a database migration is not rolled back.

## Run it

- **A shell:** `aws ssm start-session --target <instance id>`.
- **Restart a service:** run the role's rollout again, or `docker restart rush-lab-runner` (or
  `rush-lab-web`) on its VM.
- **Change a setting:** put the parameter again, then deploy, so the rollout reads it.
- **More capacity:** a larger `runner_instance_type`, and `RUNNER_MEMORY`/`RUNNER_CPUS` in
  `infra/aws/runner/run.sh` to match. NanoAgent runs 8 runs at once (`max_concurrency`).
- **A host failure:** an EC2 auto-recovery alarm moves the VM to a new host, keeping its disk and
  addresses.
- **A newer Amazon Linux:** set `image_id` in `infra/aws/deploy.yaml` to its AMI id and deploy.
  This replaces both VMs: plan for downtime, a new runner address (the stack updates
  `NANOAGENT_URL`) and Caddy getting its certificate again.
- **Run folders:** Mochi removes each run's folder once it has written it back. One it could not,
  as when Mochi restarted mid-run, is removed a day after its run last touched it
  (`infra/aws/runner/sweep.py`).

## Try it on your computer

The same containers run under Docker Desktop. Start them in this order:

1. PostgreSQL 18 on a Docker network named `rush-lab`.
2. `npm run cloud:verify` once, which builds the runner image.
3. `infra/aws/runner/run.sh rush-lab-runner:verify <env file> <data folder> 127.0.0.1:18787`.
4. `docker build --build-arg SITE_URL=https://localhost:8443 -t rush-lab-web .`
5. `WEB_HTTP_PORT=8080 WEB_HTTPS_PORT=8443 infra/aws/web/run.sh rush-lab-web <env file> localhost`,
   with `NANOAGENT_URL=http://host.docker.internal:18787` in its env file.

Caddy then serves `https://localhost:8443` with a certificate from its own local authority.
`npm start` cannot offer RUSH Lab cloud: its NanoAgent runs plugins unconfined, which
`CLOUD_RUNS` must never be set beside.

## Limits

- **Restarts.** A cloud run does not survive Mochi restarting, unlike a run held by a member's
  computer: NanoAgent stops it, and what it wrote in its folder is not written back.
- **Cancelled runs.** A run its member cancels before the model has answered is not charged.
  Each such run costs the lab at most its first model call, and starting runs is rate-limited.
- **One runner VM.** More than one needs runs routed by install.
- **Members' own keys.** Cloud runs use the lab's key and its fixed model and limits. A member's
  behaviour settings apply on their computer.
- **NanoAgent's event loop.** NanoAgent checks a plugin's lock and runs its input and output
  verifiers on its event loop, each for up to 60 s, so one slow plugin delays the others.
